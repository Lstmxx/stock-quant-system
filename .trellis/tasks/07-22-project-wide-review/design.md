# 全项目审查设计

## 审查边界

审查及修复以 monorepo 主产品为核心：React Web、Elysia API、FastAPI Engine、Drizzle/PostgreSQL 和 Redis。根目录实验脚本只检查其与主系统的交叉影响。

## 审查方法

1. 建立静态系统地图：入口、模块、数据库表、队列、内部 HTTP 接口和前端路由。
2. 建立关键链路地图：认证与用户隔离、数据采集、因子挖掘/选择、LLM 配置与调用、LLM 选股、任务状态与日志。
3. 对照仓库 ADR、领域上下文和 Trellis 工作流契约，逐链路检查事实来源、状态机、失败语义和数据形状。
4. 对高风险模式执行反向追踪：从 UI 状态追到 API、队列、Engine 和数据库约束，确认是否为真实缺陷。
5. 运行构建、类型检查、单元/集成测试和 lint，用运行结果补充静态审查。
6. 按严重度和确定性汇总，并为每项给出最小修复方向而非直接改码。

## 风险分类

- P0：可能导致大范围数据破坏、密钥泄露、跨用户访问或系统不可用。
- P1：核心工作流错误、持久状态分叉、无法恢复的任务、明显安全边界缺陷。
- P2：局部错误、性能和体验显著退化、维护成本高或测试缺口可能掩盖回归。
- P3：一致性、可读性、易用性和工程治理改进。

每个发现同时标记确定性：已验证、强证据、建议性。P0/P1 必须通过完整调用链或可执行检查复核。

## 重点契约

- 浏览器只通过 API 访问业务能力；API 负责外部认证和用户授权。
- Engine `/internal/*` 仅用于受控的内部服务协作。
- PostgreSQL 是持久状态事实来源，Redis 不应成为不可恢复的唯一业务事实来源。
- 用户拥有的配置、任务、因子、结果和策略必须按 `userId` 隔离。
- 长任务必须有一致的创建、运行、取消、失败、重试和完成语义。
- UI 必须能区分加载、无数据、部分成功、失败、取消和配置缺失。

## 兼容性与运行约束

- 修复会更改内部接口认证、Web 默认路由和 Watchlist/Strategy 数据约束，需要同步环境配置与数据库迁移。
- 依赖 PostgreSQL、Redis、行情源或 LLM 的集成检查可能受本地环境限制；报告必须明确区分环境失败和代码失败。
- 当前工作树在任务创建前是干净的；审查期间只允许修改本任务文档和最终报告。

## 交付形态

- 在任务目录内保存完整审查报告，便于后续拆分修复任务。
- 面向用户的最终摘要突出最高优先级问题和推荐实施顺序。
