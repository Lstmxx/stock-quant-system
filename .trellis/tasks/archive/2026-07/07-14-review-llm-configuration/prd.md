# 审查大模型配置模块体验与逻辑

## Goal

审查大模型配置模块从“用户创建配置”到“业务实际调用模型”的完整链路，识别用户体验、代码逻辑、安全性和跨模块一致性问题，并给出可执行、按优先级排序的优化建议。

## Background

- 配置管理入口位于 Web 的大模型管理页，数据持久化到 `llm_models`。
- 模型配置同时被因子任务、Engine 因子挖掘、个股分析和策略生成使用，但当前存在 `llm_models`、`user_configs` 与环境变量多套配置来源。
- 本轮只做审查与建议，不修改业务代码、不调用真实付费模型。

## Requirements

- R1：审查新增、编辑、删除、设为默认、列表加载及失败反馈的用户体验。
- R2：审查 API 输入验证、用户隔离、默认模型唯一性、事务一致性和错误语义。
- R3：审查 API Key 的存储、加密、脱敏、跨 Node/Python 解密及敏感信息暴露风险。
- R4：追踪模型配置在因子挖掘、个股分析与策略生成中的实际消费路径，验证页面语义与运行时行为一致。
- R5：审查 provider、modelName、baseUrl、apiKey、isDefault 字段的实际作用、兼容边界与缺省行为。
- R6：检查现有测试是否覆盖关键行为，并指出最有价值的回归测试缺口。
- R7：每个重要发现必须提供可复核的文件与行号、影响、触发场景和修复方向，避免只给原则性建议。
- R8：评估 `apps/engine/app/core/llm_backend.py::chat` 从手写 `requests` 迁移到成熟 SDK 的方案，比较 OpenAI Python SDK、LiteLLM Python SDK 与维持现状的成本、能力和兼容性。
- R9：以“真正多 Provider + LiteLLM Python SDK + 项目自有薄适配层”为目标方向，审查现有字段、调用路径和错误语义的迁移差距。

## Acceptance Criteria

- [x] AC1：输出按严重程度排序的审查发现，区分用户体验、业务逻辑、安全性和测试缺口。
- [x] AC2：完整描述 `Web -> API -> PostgreSQL -> Engine/API consumer -> LLM provider` 数据流及配置来源分叉。
- [x] AC3：确认“默认模型”是否被业务消费、不同业务是否使用同一配置来源、提供商字段是否影响请求协议。
- [x] AC4：核实默认模型切换、无效 ID、删除被引用模型、并发更新和保存失败时的实际行为。
- [x] AC5：核实 API Key 是否可能以明文、可预测密钥加密或不必要响应字段暴露。
- [x] AC6：给出分阶段优化建议，标明优先级、用户价值、改动范围及建议测试。
- [x] AC7：给出 `chat` 调用层的推荐选型、适用边界、迁移轮廓、依赖影响及测试策略。
- [x] AC8：明确 provider/model 标识映射、自定义 Base URL、无密钥本地模型、结构化输出、重试与异常归一化的目标契约。

## Out of Scope

- 不直接实现修复。
- 不使用用户真实 API Key 发起付费模型请求。
- 不评价模型输出质量、提示词质量或模型选型优劣，除非它们由配置链路错误直接导致。

## Notes

- 评审结论以当前分支源码和测试为事实依据；推断会明确标注。
- 产品决策：支持真正多 Provider；传输层采用 LiteLLM Python SDK，业务代码通过项目自有薄适配层调用。
