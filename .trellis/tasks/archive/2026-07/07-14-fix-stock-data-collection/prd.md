# 修复股票数据采集链路

## Goal

让股票数据采集任务在手动触发、定时执行、失败重试和取消场景下都能可靠地产出一致的市场数据，并向用户准确展示任务状态和错误信息。

## Background

当前采集链路横跨 Web、API、PostgreSQL、Redis 和 Engine。Review 已确认以下问题：新任务可能取消其他用户任务；定时任务依赖不存在的 `system` 用户且从多份用户配置中任取一份；失败重试没有重建下游使用的聚合行情缓存；数据库写入和 Redis 入队失败时可能遗留永久 `PENDING` 任务；部分失败及取消状态在前端会被错误展示；轮询、校验和错误反馈不完整。

## Requirements

- R1：股票数据采集采用全局唯一任务模型；同一时间至多存在一个 `PENDING`、`RUNNING` 或 `CANCELLING` 的采集任务，新的触发请求不得隐式取消现有任务。
- R2：定时采集使用唯一、确定的系统级配置和合法的任务归属，不依赖任意用户记录或隐含的 `system` 外键。
- R3：正常采集和失败重试必须最终更新同一份下游可消费的聚合行情数据；重试结果反映实际成功、失败数量。
- R4：任务持久化与队列投递失败时必须收敛到可诊断的终态，不得永久停留在 `PENDING`；Redis 连接必须可靠释放。
- R5：任务、worker 和取消流程的状态语义在 Engine、API、数据库和 Web 之间保持一致，明确区分完成、部分成功、失败、取消中和已取消。
- R6：API 对回溯天数和 worker 数量执行整数范围校验，不能仅依赖前端控件。
- R7：任务列表和进度轮询避免请求重叠、旧响应覆盖新状态及无限增长的全量历史拉取。
- R8：用户能够看到提交中、取消中、请求失败、部分失败和重试结果；重复提交受到约束，危险操作有明确说明。
- R9：新增自动化测试覆盖跨用户/全局任务并发、入队失败、部分失败、取消、重试聚合数据、调度配置以及前端关键状态流转。
- R10：本次不引入角色/RBAC；所有已登录用户都可查看、启动、取消全局采集任务及修改全局采集配置，任务保留实际发起人用于审计。
- R11：系统默认在 Asia/Shanghai 时区的工作日 20:00 执行定时采集；全局配置允许调整 cron 表达式，并在 API 与 Engine 边界校验。

## Acceptance Criteria

- [x] AC1：同时存在两个用户时，全系统至多运行一个采集任务；第二个触发请求得到明确的冲突响应，不会取消或重复创建任务。
- [x] AC2：定时任务可在没有 `id = "system"` 用户的数据库中成功创建，并使用唯一、确定的系统级调度配置。
- [x] AC3：失败股票重试成功后，下游读取的聚合行情数据包含补齐结果；失败时返回真实的成功数、失败数和错误信息。
- [x] AC4：模拟 Redis 入队失败后，数据库任务进入 `FAILED` 等可诊断终态，不存在悬挂 `PENDING` 记录。
- [x] AC5：API 拒绝零、负数、小数和超限的 `lookbackDays`、`workerCount`。
- [x] AC6：前端不再把 failed worker 显示为 completed，详情弹窗随轮询结果刷新，并正确展示 `CANCELLING`、部分成功和加载错误。
- [x] AC7：用户连续点击触发按钮不会创建意外的并发任务；取消反馈与后端真实状态一致。
- [x] AC8：任务列表支持有界查询/分页；进度轮询串行化并丢弃过期响应。
- [x] AC9：相关 API、Engine 和 Web 自动化测试通过，现有因子等下游功能没有回归。
- [x] AC10：默认定时任务明确以 Asia/Shanghai 时区工作日 20:00 执行；保存无效 cron 时返回可理解的错误且不会破坏当前调度。

## Constraints

- 保持现有 Elysia、FastAPI、Redis、Drizzle 和 React/antd 技术栈。
- 不删除用户历史任务；数据库变更需要可向前迁移并具备回滚路径。
- 市场行情聚合缓存的 key/读取契约若需调整，必须兼容现有下游消费者或同步迁移。

## Decisions

- D1：股票行情属于全系统共享数据，采集任务及其运行配置采用全局唯一模型；用户触发新任务时不自动取消已有活跃任务。
- D2：保持现有登录权限边界，不在本任务新增管理员角色；所有已登录用户均可操作全局采集功能。
- D3：定时任务默认语义沿用现有代码注释表达的“北京时间 20:00”，通过显式 Asia/Shanghai 时区消除部署环境差异。
