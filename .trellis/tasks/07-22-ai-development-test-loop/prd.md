# 建立 AI 开发自动化测试闭环

## Goal

为当前股票量化系统建立一套可由 AI 开发流程稳定执行的自动化验证闭环：功能完成后，能够按风险选择单元测试、跨服务集成测试、真实或高保真数据验证，以及 Playwright 页面流程测试，并把结果作为任务完成与合并前的证据，而不是依赖人工口头确认。

## Background

- 项目是包含 Web、API、Python Engine、数据库与外部行情/LLM 依赖的多包系统。
- 仓库已有 57 个 API/数据库 Bun 测试、36 个 Web Vitest 测试和 59 个 Engine Pytest 测试；当前确定性测试、构建和 Ruff 可并行在约 6 秒内完成。
- 仓库没有统一根测试命令、Playwright、浏览器测试、`.github/workflows/` 或可被 AI/CI 共同调用的完成门禁。
- 唯一真实行情测试需要 `RUN_REAL_DATA_INTEGRATION=1`，会访问真实 Redis/Baostock，并允许等待 1,200 秒；它不适合作为每次 PR 的普通门禁。
- Playwright 官方建议控制数据库、隔离测试状态并避免在普通浏览器测试中依赖不可控第三方；Cal.com 与 Immich 等成熟项目采用受控 `webServer`/Compose、保守 worker、CI 重试和失败 Trace。
- 本任务先调研社区成熟方案并形成规划，不在规划获批前实施。

## Requirements

- 盘点现有测试、运行脚本、服务编排、数据依赖和 CI 能力，明确缺口。
- 设计分层测试策略，至少覆盖快速本地反馈、服务集成、浏览器关键路径和真实数据验证。
- 明确“真实数据”的用途、可重复性、凭据隔离、成本、速率限制、失败归因和 CI 运行频率。
- 设计 Playwright 测试环境，包括服务启动、数据库准备、测试身份、固定测试数据、失败产物与调试方式。
- 将测试门禁嵌入 Trellis/AI 开发流程，使任务只有在可验证证据满足要求后才能结束。
- 参考社区成熟实践，并说明选型、取舍、阶段划分、迁移与回滚方案。
- 普通完成门禁不得调用付费 LLM Provider；LLM 页面流程使用本地、确定性的 OpenAI-compatible 测试替身。
- 全栈 Playwright 测试必须经过真实 Web、API、Engine、PostgreSQL 和 Redis；不得以拦截第一方 `/api/*` 请求代替跨层验证。
- 真实行情验证必须与确定性门禁分轨，并能够区分产品回归、基础设施故障和外部 Provider 故障。

## Acceptance Criteria

- [ ] 形成基于仓库实际结构的现状与缺口清单。
- [ ] 形成测试金字塔/测试矩阵，列出每层的目标、数据来源、触发条件、耗时预算和失败处理。
- [ ] 形成真实数据测试与确定性测试的边界及安全策略。
- [ ] 形成 Playwright 关键用户旅程、环境生命周期和可观测性方案。
- [ ] 形成与 Trellis、开发命令及 CI 对接的质量门禁方案。
- [ ] 形成分阶段、可独立验收的实施计划及验证命令。
- [ ] 所有关键技术建议均有官方文档或成熟社区实践依据。
- [ ] 形成可由 Trellis/AI 与 GitHub Actions 共同调用的稳定根命令契约。
- [ ] 规划明确失败时应保留的 Playwright Trace、截图、报告和服务日志，并禁止提交认证状态文件。

## Out of Scope

- 在规划审批前直接引入 Playwright、修改 CI 或编写测试用例。
- 以不受控的生产数据或生产写操作作为常规测试依赖。
- 在自动化流程中默认调用真实付费 LLM Provider。
